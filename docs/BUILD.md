# Build and use the standalone implementation

Implementation version: 0.1.0, unreleased. C++20, 64-bit little-endian arm64/x86_64.
Physical qualification remains unavailable.

## Native core, converters and diagnostics

```sh
python3 tools/fetch_dependencies.py
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build -j12
ctest --test-dir build --output-on-failure -j12
python3 tests/test_converters.py
./build/aa_tests build/fixtures --qualification
```

Fetching dependencies is an explicit build provisioning step, with pinned archive
SHA-256 verification. Runtime and data converters never download anything. Build
production with `AA_BUILD_TESTS=OFF`, `AA_BUILD_TOOLS=OFF` and
`AA_BUILD_DIAGNOSTICS=OFF`. `astroattitude` is the static C++ library;
`astroattitude_c` is the shared C ABI; `astroattitude_c_static` supports static
adapter packaging. Installed CMake consumers use `find_package(astroattitude CONFIG REQUIRED)` and targets `astroattitude::core`, `astroattitude::c`, or `astroattitude::c_static`. The static core retains its ERFA link dependency. No Eigen or JSON types appear
in installed public headers. Use `cmake --install build --prefix <destination>`.

`AA_SANITIZE=ON` enables address and undefined-behavior sanitizers. Allocation
fault injection is a separate executable and is never linked into production.
`AA_BUILD_DIAGNOSTICS=ON` builds `aa_benchmark`; it uses only synthetic resources.
The core test creates fixtures under its supplied directory (default `fixtures`
relative to its working directory). Those files are explicitly synthetic and
must never become application provisioning assets.

For standalone C and C++ examples, enable `AA_BUILD_EXAMPLES=ON`; run `aa_c_example` or `aa_cpp_example` with the generated catalog, astrometry and request JSON paths.

## Swift

```sh
sh tools/build_apple.sh
swift run --package-path bindings/swift -j 12 synthetic-example "$PWD/build/fixtures"
```

The script builds macOS host architecture (minimum 13), iOS arm64 and iOS simulator host architecture
(minimum 16), then creates `bindings/swift/Artifacts/CAstroattitude.xcframework`.
The Swift package has typed Codable values, typed semantic failures, engine and
cancellation objects. Calls are synchronous. Explicit `close()` waits for active
calls and is idempotent; ARC also releases native handles. The package links libc++.
`WireUInt64` and `WireInt64` preserve the exact decimal-string C wire convention;
their public `value` properties are UInt64 and Int64.

## Python 3.9+

```sh
PYTHONPATH=bindings/python python3 examples/python_synthetic.py \
  "$PWD/build/libastroattitude_c.dylib" "$PWD/build/fixtures"
python3 tools/package_python.py build/libastroattitude_c.dylib dist/python-macos-arm64
```

Use `.so` on Linux. The packaging command copies the typed ctypes package, the
same compiled native implementation, its hash manifest and notices into a fresh
output directory. It does not publish a package or claim a universal wheel.
`NativeLibrary(path)` makes native-binary selection explicit; no search of global
library directories or numerical Python fallback occurs. `Engine` and
`CancellationToken` support context managers and idempotent `close()`.
`AttitudeSolution | SolverError` represents semantic outcomes. `AbiError` and
`ResourceError` preserve ABI failures and resource-creation rejection separately.

## Android

Prerequisites: JDK 17+ (validated with 21), SDK platform/build-tools 36, and NDK
27.0.12077973. Gradle 8.13, AGP 8.13.2, Kotlin 2.2.21 and kotlinx.serialization 1.9.0
are pinned. Gradle's distribution checksum is pinned in the wrapper.

```sh
export ANDROID_HOME=/path/to/android/sdk
sh tools/build_android.sh
cd bindings/android
./gradlew :library:assembleRelease :library:assembleDebugAndroidTest :example:assembleRelease
```

Native compilation is an explicit step before Gradle packaging. The AAR contains
one `libastroattitude_jni.so` per ABI (`arm64-v8a`, `x86_64`), statically linked
with libc++, the C ABI and the core. Only JNI entry points are exported. Minimum
API is 26; example compile/target API is 36. R8 consumer rules preserve JNI lookup
names and the bridge exception constructor. Example signing uses the standard local Android debug keystore, generated by the
Android tooling. It is for emulator validation only; no signing key is distributed.

The example is a standalone synthetic app with no camera, location or network
permissions. Generate fixtures with the native test first. The library itself
contains notices, not synthetic catalog or EOP assets. Kotlin callers choose their
thread or coroutine dispatcher. `Engine` and `CancellationToken` implement
`Closeable`; `.use {}` is recommended. Shared read leases protect active solves;
close acquires an exclusive lease and rejects subsequent use. IDs use a
`WireUInt64(ULong)` value, including ULong.MAX_VALUE. JNI passes byte arrays, not
modified-UTF-8 strings. Native bridge exceptions are distinct from
`SolveOutcome.Failure`.

NDK flexible page-size support and both `max-page-size=16384` and
`common-page-size=16384` are enabled. Check ELF LOAD alignment and GNU_RELRO end
alignment, then check the consuming APK with `zipalign -c -P 16 4`. Actual emulator
execution is required separately; ELF alignment alone is insufficient. See
[Android guidance](https://developer.android.com/guide/practices/page-sizes).

The pixel path uses the conservative Brown branch certificate implemented by the native resource and geometry checks. Strong distortion may be rejected even when an inverse exists; the ray API remains available for independently calibrated optics.

## Offline data conversion

`tools/convert.py` accepts local source files only. `--inputs` names a local JSON
array; each item contains `path` and the resource source metadata fields except
`source_sha256`, which the converter computes. Paths resolve relative to that
metadata file. Include provenance for every supporting format/rights document.

```sh
python3 tools/convert.py hipparcos --inputs /local/catalog-inputs.json \
  --valid-from 1577836800 --valid-until 1577923200 --output /local/catalog.json
python3 tools/convert.py astrometry --inputs /local/time-inputs.json \
  --valid-from 1577836800 --valid-until 1577923200 \
  --announcement-valid-until 1578009600 --output /local/astrometry.json
```

These dates only illustrate syntax. The application must choose its qualified
validity and reviewed announcement bound. Output consists of a package, exact-byte
manifest and separate hash record, created exclusively without overwriting files.
The Hipparcos importer applies the audited H-field/quality selection, preserves
proper motion, propagates all six parameters with pinned ERFA, and rejects every
nonzero propagation status. The EOP importer chooses a complete B triple or an A
triple with both flags; it rejects blank placeholders as coverage. Leap expiry and
announcement bounds are intersected. Rights remain `not_evaluated`: conversion
neither approves intended use nor grants redistribution permission. Applications must review source rights before distributing resource packages.

## Platform parity checks

After the native CTest suite has generated its fixtures:

```sh
PYTHONPATH=bindings/python python3 tests/test_python.py build/libastroattitude_c.dylib build/fixtures
swift run --package-path bindings/swift -j 12 calibration-guide build/fixtures/catalog.json build/fixtures/astrometry.json build/fixtures/workflow-training.json
python3 tools/test_ios_simulator.py
```

The iOS script requires a locally installed iOS simulator runtime and an available
iPhone simulator device template. It creates, boots and removes its own temporary
simulator. It never installs on a physical device. Build the XCFramework first.
On Linux use `.so` for the Python test.

Android instrumentation uses the same generated fixtures. After the Android builds,
run `:library:connectedDebugAndroidTest` with a dedicated emulator selected via
`ANDROID_SERIAL`; do not select a physical phone. `tools/verify_android.py` accepts
the SDK directory and checks both ABIs, AAR contents and APK alignment.
